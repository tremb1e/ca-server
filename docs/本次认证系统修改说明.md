# 2026-07-13 磁力计质量检测与动态 6/9 轴

- 新增用户级磁力计质量报告 `processed_data/z-score/<user>/sensor_mode.json`。
- 对 `sqrt(mag_x²+mag_y²+mag_z²)` 使用 `120µT` 固定阈值；超限比例大于 `1%`、有效覆盖率低于 `95%` 或有效样本少于 `100` 时使用 6 轴，否则使用 9 轴。
- 阈值来自参考用户前 300MB 数据实测；按实际重采样判定数据，参考用户 P99 为 `113.80µT`、超限比例 `0.515%`。两个待重训用户的超限比例为 `41.318%`、`17.870%`，均选择 6 轴。
- scaler 只处理入模列；训练命令显式携带 `--input-height`；checkpoint 复用、policy search、离线/在线推理和模型就绪检查均校验或读取同一轴数。
- `input_height=6` 和 `9` 都是当前合法模型；旧的 `12` 轴模型仍拒绝。
- 完整算法、统计证据和配置说明见 `docs/磁力计质量检测与动态轴数说明.md`。

# 2026-06-29 认证聚合窗口阈值与并发能力修订

日期：2026-06-29

本次修订聚焦两件事：（1）让 App 端展示的认证聚合窗口阈值（“M of N”）来自 `ca_config.toml [auth]` 配置而非 per-user 策略文件；（2）把训练/推理并发默认值调整为“支持 100 并发用户”。两项改动均已通过单元/集成测试（148 个 pytest 用例通过）。本次仅改默认值与权威来源，不改 proto、不引入任何二次迟滞/二次投票。

## 一、认证聚合窗口阈值改为以 ca_config.toml 为权威来源

- 现象：App 端展示的 “M of N” 此前来自 per-user `models/<user>/best_lock_policy.json`（`policy_search` 为该用户产出的投票窗口，例如 “5 of 9”），而不是 `ca_config.toml [auth]` 配置，导致展示值与配置不一致。该串文案承载在 `AuthResult.message`（proto 字段 13），本次未改 proto。
- 修复（代码）：`src/authentication/manager.py` 的 `_policy_from_config()` 改为以 `ca_config.toml [auth]` 为权威来源——`decision_strategy` / `vote_window_size` / `vote_min_rejects` / `ema_alpha` 覆盖 per-user 策略；per-user `best_lock_policy.json` 仅继续提供该用户“单窗口原始分数阈值 `threshold`”与模型工件路径（checkpoint / config）。
  - 新增告警：当 `decision_strategy="vote"` 且 `vote_window_size` 与 `result_delay_sec` 折算的发布窗口数不一致时打日志告警；当投票阈值非法（要求 `0 < vote_min_rejects <= vote_window_size`）时打日志告警。
- 修复（配置）：`ca_config.toml` 与 `deploy/config/ca_config.toml` 的 `[auth]` 设为 `decision_strategy="vote"`、`vote_window_size=50`、`vote_min_rejects=30`，与 `result_delay_sec=5.0` 折算的 50 窗对齐（0.2s 窗 + 50% overlap => stride 0.1s => 5s = 50 窗）。于是 App 端展示 “30 of 50”。
- 语义不变（重要）：仍是**单一 primary 阶段，没有二次迟滞 / 二次投票**（`result_stage` 始终为 `"primary"`）。`result_delay_sec` 仅做“发布节流”（每累计 50 窗向 App 回包一次，期间只回 `Ack`）；vote 50/30 是对这 50 窗的聚合判定。二者窗口数应保持一致（均为 50）。
- 新增测试：`tests/unit/test_policy_config_override.py`（含端到端：满 50 窗后回包 `message` 为“近50窗恶意 50/50，阈值 30”、`interrupt=True`、`result_stage=primary`）。

## 二、支持 100 并发用户同时训练与推理

- 并发模型（务必准确理解）：服务端为 asyncio + `grpc.aio`。
  - 训练：用户提交是“无限接纳 + 队列”——每个用户一个 asyncio 任务，真正同时在 NPU 上执行的训练数由 `TrainingManager` 的 `asyncio.Semaphore(training_max_concurrent)` 限制，超出上限的在信号量上排队。
  - 推理：由 `AuthSessionManager._inference_semaphore = asyncio.Semaphore(auth_max_concurrent)`（NPU 前向）+ per-user 模型 LRU 缓存 `auth_max_cached_models` + `grpc_max_concurrent_rpcs`（每条 `StreamSensorData` 长流计 1 个 RPC）共同约束。
  - 根因：此前 `deploy/config/server.env` 的 `TRAINING_MAX_CONCURRENT=1` 覆盖了代码默认 8，导致只能单用户串行训练。
- 修复（代码默认值，`src/config.py`）：`auth_max_concurrent` 16→100、`auth_max_cached_models` 16→100、`grpc_max_concurrent_rpcs` 256→512；`training_max_concurrent` 保持 8。
- 修复（env，`deploy/config/server.env` 与 `server.env.example`）：`TRAINING_MAX_CONCURRENT` 1→8、`AUTH_MAX_CONCURRENT` 16→100、`AUTH_MAX_CACHED_MODELS` 16→100、新增 `GRPC_MAX_CONCURRENT_RPCS=512`。
- 设计与 NPU 硬件约束：服务器为 8 卡 Ascend 910B。训练是重负载（每个训练占 1 卡 + 数 GB 显存 + CPU 预处理进程池），8 卡无法真正“同时”跑满 100 个训练而不 OOM。因此采用“**接纳 100 + 安全并行**”：100 个用户全部被接纳并排队，真正同时在 NPU 上训练的数量限为 `TRAINING_MAX_CONCURRENT`（默认 8 = 每卡 1 个，可在 `server.env` 调大，前提是单卡显存能容纳 `ceil(值/卡数)` 个训练），其余自动排队——既“支持 100 并发用户”又不 OOM。
- 推理为小模型瞬时前向，100 并发可行（实际同时计算数还受 asyncio 默认线程池约束，但对约 1 包/秒/用户的负载足够）。已知点：推理模型缓存当前都在 `npu:0`，训练会 round-robin 占用 `npu:0..7`，`npu:0` 上训练与推理共享，属可接受的已知现象。
- 边界澄清：`ca_config.toml [training] max_parallel_train` 只影响离线 / CLI 多用户 sweep（多设备池分配），不影响 server 单用户训练路径（server 每次只训练 1 个用户、1 个窗口尺寸），不是 server 的并发开关。
- 新增测试：`tests/unit/test_concurrency_wiring.py`。

# 2026-06-29 本轮修改（历史）

日期：2026-06-29

本轮聚焦“VQGAN 输入瘦身、策略发布与上线校验加固、认证结果尺度拆分，以及若干训练死锁/设备 ID 解析缺陷修复”。本轮改动与 2026-05-29 之前的 9 轴模型、旧策略文件不兼容，需重新生成窗口数据、重新训练 VQGAN、重新跑 `policy_search`。

## A. VQGAN 输入由 9 轴改为 6 轴（历史行为，已被 2026-07-13 动态 6/9 轴取代）

- 模型输入由 `(1, 9, T)` 改为 `(1, 6, T)`；6 行 = 加速度计 `acc_x/y/z` + 陀螺仪 `gyr_x/y/z`，不再使用磁力计 `mag_x/y/z`。
- 模型 config 的 `input_height` 由 9 改为 6（`image_channels` 仍为 1）。
- 数据处理 / 数据集生成：窗口 CSV 的传感器列与 z-score scaler 现为 6 列（`FEATURE_COLUMNS` 去掉 `mag`）；数据重采样不再要求磁力计存在。
- 兼容性：所有此前的 9 轴模型 / scaler / 策略均不兼容，必须重新生成窗口数据、重新训练 VQGAN、重新跑 `policy_search`。
- 涉及处：`ca_train/hmog_data.py`、`ca_train/vqgan` 的 encoder/decoder（`input_height` 默认值）、`src/processing/pipeline.py`、`src/processing/scaler.py`、`src/authentication/vqgan_inference.py`、`src/training/runner.py`(`_vqgan_config`)；各处 `input_height` 校验由 `!= 9` 改为 `!= 6`。

## B. 重构策略发布流程

- 训练阶段不再写正式 `best_lock_policy.json`，改写 `training_fallback_policy.json`，并标记：
  - `policy_status = "training_fallback"`
  - `policy_search_completed = false`
  - `score_metric = "mse"`
  - `score_scale = "negative_reconstruction_error"`
  - `threshold_strategy = "training_val_genuine_threshold"`
- `policy_search` 成功后“原子写入”（先写 `.tmp`，再 `os.replace`）`best_lock_policy.json`，新增字段：
  - `policy_search_completed = true`
  - `policy_status = "ready"`
  - `score_metric = "mse"`
  - `score_scale = "negative_reconstruction_error"`
  - 并落盘 `genuine_score_stats`：来源为 val 上真实用户分数统计，含 `count / min / max / mean / std` 以及 `quantiles{0.001, 0.01, 0.05, 0.5, 0.95, 0.99, 0.999}`。
- 认证启动仅接受 `policy_status = "ready"` 且 `policy_search_completed = true` 的正式策略；新增配置开关 `auth.allow_training_fallback_policy`（默认 `false`），开启后允许在缺少正式策略时显式回退到 `training_fallback_policy.json`（降级运行）。
- 旧策略（无 `policy_status` 字段）向后兼容：
  - 含 `grid_search` 或 `threshold_strategy = "interrupt_window_frr"` 的旧策略推断为 `ready`；
  - 文件名为 `training_fallback_policy.json` 的推断为 `training_fallback`；
  - 其余裸旧策略推断为 `legacy`（不就绪）。

## C. 加固 check_trained_model（模型上线校验）

- 阈值必须为有限值：拒绝 `inf` / `nan` / `sys.float_info.max` 及 `|阈值| >= 1e6` 等异常值。
- 策略必须包含 `threshold_strategy`、`decision_strategy`、`score_metric`、`score_scale` 四个字段。
- 校验 checkpoint / scaler / config / policy 的指纹（sha256 取前 1MB）与 mtime；会话启动时把校验详情写入 `inference/<device>/<session>/model_validation.json`。
- 校验阈值落在训练 / 验证集 genuine 分数分位范围附近（带 margin），明显越界则拒绝上线。
- `has_trained_model` 现委托 `check_trained_model`；gRPC `StartAuthentication` 调用 `check_trained_model` 取得 `(是否就绪, 原因)`。

## D. 拆分认证结果字段（避免尺度混读）

- 迟滞 / EMA 决策结果同时写出三套尺度：
  - `raw_score` / `raw_threshold`：原始分数尺度；
  - `ema_score` / `ema_threshold`：EMA 尺度；
  - `display_score` / `display_threshold`：0~1 可视化尺度。
- 返回 payload 与管理接口均带 `result_stage`（当前恒为 `"primary"`）；管理结果（`/auth/results` 与 `/auth/results/latest`）默认按 stage 分组返回 `by_stage` 字段。
- 旧字段 `score` / `threshold` / `normalized_score` 保留为兼容字段；管理结果读取还会把历史记录的 `decision_score` / `decision_threshold` / `decision_accept` 归一映射到 `score` / `threshold` / `accept`。

## E. 修复模型不可用时训练状态死锁

- 当某用户没有可用模型（从未训练 / 训练中断 / 已完成但校验不通过）时，App 触发 `StartAuthentication` 会以 `force=True` 强制（重）训练；`force` 触发会绕过节流与“持久化 `in_progress` 但无存活任务”的死锁判定。
- window sweep 跑完但没有产出认证可接受的正式策略时，会抛出 `PolicySearchIncompleteError`，训练状态记为 `failed`（可被再次触发重训），不会假装训练成功。

## F. 修复横杠开头设备 ID 训练失败

- 形如以 `-` 开头的 base64 设备哈希会被 argparse 当作选项导致训练失败。新增 `src/utils/cli_args.py` 的 `normalize_option_value_args`，把 `--user -X` 规整为 `--user=-X`；训练子进程改用 `--users=<id>` 形式传参。四个 CLI（training / auth / policy-search / processing）均已接入。

## G. 本轮注意事项

- 旧 9 轴 checkpoint、scaler 与阈值不能继续作为线上模型使用；上线前必须重新生成 6 轴窗口数据、重新训练并重新运行 `policy_search`。
- 仅当 `auth.allow_training_fallback_policy = true` 时，缺少正式策略才允许以 `training_fallback_policy.json` 降级运行；默认 `false`，未完成 `policy_search` 的用户不会被接受进入认证。
- 认证结果字段已按尺度拆分，管理端 / App 端展示分数时应明确选择 `raw_*`、`ema_*` 或 `display_*`，不要把不同尺度混读。

- `vqgan_inference.py` 会拒绝 `input_height != 9` 的模型配置。
- `has_trained_model()` 和管理快照会把旧 12 轴模型判定为不可用。
- 因输入分布变化，全部用户模型需要重新训练，阈值需要由新的 `policy_search` 重新标定。

## 4. 训练、早停与日志

配置入口：

- `[training].max_epochs = 50`
- `[training].early_stop_patience = 3`
- `[training].batch_size = 128`
- `[training].device = "auto"`
- `[training].max_parallel_train = 8`
- `[training].run_policy_search = true`

核心实现：

- `src/training/manager.py`
- `src/training/runner.py`
- `ca_train/hmog_vqgan_experiment.py`

训练行为：

- 默认最多训练 50 epoch。
- 验证集 AUC 连续 3 次不提升时早停。
- 每个 epoch 记录 train / val / test 关键指标。
- 训练结束恢复最佳 epoch 权重。
- 训练完成后默认调用 `policy_search`，将验证集上选出的策略写入模型目录。

NPU 并行：

- `src/utils/accelerator.py` 支持 `auto / npu:<id> / cuda:<id> / cpu`。
- `device=auto` 优先选择 NPU，其次 CUDA，最后 CPU。
- 多用户训练任务按 `device_pool()` 分配到可见设备。
- 在 8 卡 Ascend 910B 环境中，默认设备池为 `npu:0` 到 `npu:7`。

## 5. 策略搜索与线上打通

涉及文件：

- `src/policy_search/runner.py`
- `src/policy_search/cli.py`
- `src/authentication/runner.py`
- `src/authentication/manager.py`
- `src/utils/reject_trackers.py`

当前策略：

- 默认 `decision_strategy = "ema"`。
- 保留 `vote`，即 y-of-x 投票机制。
- 保留 `k`，兼容旧的连续 K 次拒绝。

EMA 策略：

- 对 VQGAN 原始窗口分数做指数滑动平均。
- `ema_alpha` 默认来自配置，最终每用户可由 `policy_search` 在验证集上选择。
- 目标是在不明显牺牲攻击检测的前提下降低真实用户短时波动造成的 FRR。

policy_search 输出：

```text
models/<user>/best_lock_policy.json
models/<user>/policy_search/grid_results_vqgan_only.csv
models/<user>/policy_search/pareto_frontier_vqgan_only.csv
models/<user>/policy_search/best_lock_policy_vqgan_only.json
```

线上消费：

- 在线认证优先读取 `models/<user>/best_lock_policy.json`。
- 读取 `decision_strategy`、`threshold`、`ema_alpha`、`vote_window_size`、`vote_min_rejects` 等字段。
- 当前线上打分为 VQGAN-only，因此默认 `policy_search_auth_method = "vqgan-only"`，避免离线 transformer 分数与线上 VQGAN 分数错位。

离线认证结果字段：

- `score`
- `ema_score`
- `decision_strategy`
- `raw_accept`
- `decision_accept`
- `accept`
- `interrupt`
- `consecutive_rejects`
- `vote_recent_windows`
- `vote_recent_rejects`

## 7. 配置参数说明

`[processing]`：

- `min_total_mb`：触发预处理和训练的原始数据阈值，默认 300MB。
- `target_total_mb`：实际选择处理的数据量目标，默认 300MB。
- `train_ratio / val_ratio / test_ratio`：真实用户数据切分比例。
- `workers`：单用户内部处理 worker 数。
- `process_user_workers`：多用户处理并发数。
- `hmog_val_subject_count`：验证集使用的 HMOG 用户数。
- `hmog_test_subject_count`：测试集使用的 HMOG 用户数。
- `hmog_min_subject_count`：每侧 HMOG 用户数下限。
- `hmog_session_count`：每个 HMOG 用户候选 session 数，默认 24。
- `hmog_balance_ratio`：HMOG 与真实用户数据体量比例，默认 1.0。
- `hmog_max_rows_per_subject / hmog_max_rows_total`：HMOG 行数上限，默认 0 表示不限。

`[windows]`：

- `sizes`：窗口长度列表，当前默认 `[0.2]`。
- `overlap`：滑窗重叠率，默认 0.5。
- `sampling_rate_hz`：重采样频率，默认 100Hz。

`[auth]`：

- `max_decision_time_sec`：期望首次打断决策时间上限。
- `result_delay_sec`：认证结果发布延迟（秒），默认 `0`（每个数据包都回结果，兼容旧行为）。设为 `5` 表示累积约 5s≈50 个窗口后，按该用户策略（EMA / y-of-x）聚合再向 App 回一次包，发布间隔内的数据包只回 `Ack`；全量窗口仍逐窗落盘。折算窗口数 `target_windows = round(result_delay_sec / stride_sec)`，`stride_sec = window × (1 - overlap)`，实现见 `src/utils/reject_trackers.py` 的 `windows_for_delay` / `ResultEmitGate`。
- `decision_strategy`：`ema`、`vote` 或 `k`。本 `[auth]` 配置为运行时权威来源，会覆盖 per-user `best_lock_policy.json` 中的同名字段（per-user 策略仅继续提供该用户“单窗口原始分数阈值 `threshold`”与模型工件路径）。当前部署配置为 `vote`。
- `vote_window_size / vote_min_rejects`：y-of-x 投票参数（即 App 端展示的 “M of N”）。当前部署为 `50 / 30`（“30 of 50”），与 `result_delay_sec=5.0` 折算的 50 窗对齐；当 `decision_strategy="vote"` 且二者不一致或阈值非法（要求 `0 < vote_min_rejects <= vote_window_size`）时，会话启动会打日志告警。
- `ema_alpha`：EMA 默认平滑系数。
- `ema_alpha_candidates`：policy_search 的 EMA 候选值。
- `target_window_frr`：窗口级 FRR 约束。
- `max_genuine_first_interrupt_p`：真实用户在目标时间内被误打断概率约束，可选。
- `policy_search_auth_method`：默认 `vqgan-only`。

`[training]`：

- `max_epochs`：最大训练轮数，默认 50。
- `early_stop_patience`：早停耐心值，默认 3。
- `batch_size`：训练 batch size。
- `device`：默认 `auto`。
- `max_parallel_train`：最大并行训练任务/设备数，默认 8。
- `run_policy_search`：训练结束后是否自动运行策略搜索。

## 11. 注意事项

- 旧 12 轴 checkpoint 与旧阈值不能继续作为线上模型使用。

- 本轮用户数据烟测为了快速完成使用了较小数据阈值和 HMOG 行数上限，不能代表完整生产训练性能。
- 生产环境建议保留 `INSTALL_TORCH_NPU=1`，并确保宿主机 Ascend driver/toolkit 与容器挂载路径一致。
